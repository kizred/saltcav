# AGENTS.md — SaltCav, разработка версии 2.0

Этот файл Codex читает автоматически в начале каждой сессии. Другой
истории нет — этот файл и репозиторий единственный контекст. Сначала
ПРОЧИТАЙ РЕПОЗИТОРИЙ (`git fetch origin && git log --oneline -20`,
README.md, CHANGELOG.md, docs/roadmap-2.0.md, docs/decisions.md,
docs/progress.md) и сверь с этим файлом. Если расходится — реальность
важнее, но скажи об этом в первом ответе.

## 1. Что это за проект

SaltCav — оркестратор автономной команды агентов на VPS (FastAPI +
PostgreSQL), репозиторий kizred/saltcav. Источник правды — GitHub,
ветка `main`. Релиз 1.2.0 выпущен (тег 1.2.0, merge-коммит 5360e15).
Работаем к версии 2.0. План — docs/roadmap-2.0.md, это источник
правды по задачам.

## 2. Экономия токенов (железные правила)

- Одна сессия = один пункт дорожной карты. Никаких марафонов.
- Старт сессии: короткий бриф владельца (~150 токенов) + этот файл.
- pytest всегда `-q --tb=short -x`, только итог и traceback упавшего
  теста; `git diff` — только `--stat` или по конкретным файлам.
  Полные логи не выводить.
- Файлы читать по символам/диапазонам строк, не целиком, если это
  не нужно для задачи.
- Линтеры и форматтеры — только по затронутым файлам, не по проекту.
- Длинные выводы — в файл (`> out.log 2>&1`), смотреть хвост
  (`Get-Content out.log -Tail 30`).
- Отчёт в конце сессии — не больше 15 строк.
- Если сессия явно жрёт токены больше обычного — остановись,
  отчитайся, владелец разобьёт задачу.
- Контроль расхода: если накопленный контекст сессии явно велик
  (много файлов прочитано, много итераций) — остановись, отчитайся,
  владелец разобьёт пункт. Длинная сессия хуже двух коротких.
- Не читай файлы целиком без необходимости: сначала оглавление/символы,
  потом нужный диапазон строк.
- Один вывод команды — не больше 30 строк (хвост файла, --stat).
- Не запускай полный прогон тестов чаще, чем после осмысленного изменения.
- Запрос-счёт: если в сессии перевалило ~50 запросов — остановись,
  отчитайся, владелец разберёт пункт. 352 запроса в одной сессии —
  пример, как делать не надо.

## 3. Автономность

- Работаешь в Full Auto, без запросов подтверждений.
- МОЖЕШЬ: ветки `task/SC-0NN` от свежего main, коммиты (стиль — по
  `git log`), пуш веток задач, открытие PR с телом `Closes #NN`,
  починку красного CI на своих ветках.
- НЕ МОЖЕШЬ без явной команды владельца: push в main, merge PR,
  теги, релизы, удаление тестов, изменение ядра геометрии/решателя
  и YAML-схем.
- Тег 2.0 и merge release-ветки — только владелец, вручную, в конце.

## 4. Отчётность по пункту (обязательно перед закрытием сессии)

Какой пункт брать: источник правды — docs/roadmap-2.0.md. В брифе
владелец называет этап или конкретный пункт. Если назван только этап —
берёшь первый неотмеченный пункт именно этого этапа, в порядке
документа. Не отклоняйся к другим разделам.

1. Галочки: в docs/roadmap-2.0.md проставь `[x]` на реально
   выполненные и покрытые тестами пункты, формат:
   `- [x] (YYYY-MM-DD, PR #NN) текст пункта`. Частично сделанное НЕ
   отмечать — опиши, что осталось.
2. Прогресс и заметки: отчёт по сессии (что сделано, какие тесты,
   что осталось, ≤ 15 строк) — в docs/progress.md, в конец файла,
   с датой и номером пункта.
3. Решения: каждое принятое тобой проектное решение (выбор
   представления, библиотеки, формата, компромисс) — записью в
   docs/decisions.md: дата, контекст, решение, почему.
4. Всё это — коммитом в ветку `task/SC-0NN`, уезжает в main с PR.
